FEATURE VALUES AND VARIATION POINTS

- A feature valueType is Boolean or enumeration.
- Enumeration features define distinct allowedValues and a defaultValue.
- Each feature is classified as external or internal variability.
- A configuration records Boolean and enumerated values in featureValues; effective selection still controls hierarchy and group validity.
- One reusable variation point may constrain multiple model elements or multiple relationships.
- Realization scope defaults to the entire architecture-compatible model; users may explicitly narrow it to requirements, structure, behavior, process, resources, or verification, and scoped realization produces a warning.
- A variation point condition combines the safe Boolean feature-expression grammar with zero or more typed feature-value conditions.
- Supported variation-point kinds are Existence, Primitive Property, Primitive Tag, and Element Property.
- Existence includes its targets when the condition is true and removes them when false.
- Modification kinds use ordered value rules and whitelisted property paths; the first matching rule supplies the realized value.
- Primitive Property supports safe scalar model fields, selected process/resource metadata, parameter values, and relationship quantity/name fields.
- Primitive Tag supports custom-attribute scalar values and string tags.
- Element Property supports safe element-reference retargeting such as relationship sourceId/targetId and architectureId.
- Element Tag effects that require a stereotype/tag metamodel with element-valued references remain out of scope.
- Never infer applicability from names or topology. Unconstrained content is common.
- Never execute JavaScript, Python, Ruby, or arbitrary expressions.

CONFIGURATION SELECTION MODEL

Configuration uses:
- manuallySelectedFeatureIds: direct user intent;
- effectiveSelectedFeatureIds: root, manual selections, and deterministic mandatory selections;
- autoSelectedFeatureIds: effective minus manual.

Rules:
- manuallySelectedFeatureIds never stores automatic selections unless the user explicitly selected the same feature;
- root is effective and automatic unless the user interface treats it as fixed;
- mandatory children of active parents are selected automatically;
- mandatory children cannot be effectively deselected while their parent is active;
- inactive branches do not force descendants;
- deselecting a parent removes all descendants from manual, automatic, and effective selections;
- invalid XOR, OR, requires, and excludes states remain visible for correction;
- validation and derivation always use effectiveSelectedFeatureIds;
- the UI distinguishes manual, automatic, and invalid states with text or icon in addition to color.

150%-TO-100% DERIVATION

Use this exact algorithm:
1. Validate configuration.
2. If invalid, stop and show actionable errors.
3. Build architecture-compatible source element and relationship sets.
4. Treat targets without an enabled Existence variation point as common.
5. Evaluate every enabled Existence variation point against effectiveSelectedFeatureIds and typed featureValues.
6. Include constrained targets when every applicable Existence condition is true; otherwise exclude them.
7. Remove relationships explicitly excluded by an Existence variation point or whose realized endpoint does not exist.
8. Evaluate active Primitive Property, Primitive Tag, and Element Property variation points in deterministic array order.
9. For each active modification, apply the first matching ordered value rule to a cloned target using only its whitelisted property path.
10. Block unsupported property paths, missing targets, missing rules, invalid conditions, and conflicting modifications.
11. Record removed element/relationship IDs, modified element/relationship IDs, and every applied effect with variation point ID, target, property path, previous value, and realized value.
12. Warn when relationship cleanup cascades from removal and ask the user to review remaining traceability completeness.
13. Run model-quality validation against the realized subset.
14. Calculate applicable KPI values against the realized subset, including modified values.
15. Create a new immutable DerivationResult containing both the untouched source snapshot and cloned realized element/relationship snapshots.
16. Store sourceProjectId, sourceArchitectureId, configurationId, sourceModelRevision, timestamp, selected feature IDs, typed feature values through the configuration, validation results, and KPI results.
17. Do not mutate the source 150% model.
18. Do not silently overwrite historical derivations; configuration.derivation may point to the latest derivation while old simulation records retain their referenced derivation snapshots.

STANDARD PRE-SIZING ALGORITHMS

Run only on:
- selected architecture;
- and, when provided, selected valid derivation/configuration.

Active data means the architecture-compatible source subset or the selected derived subset.

Total mass:
- sum active numeric parameters with semanticKey = "mass";
- require consistent units;
- sample uses kg.

Direct element cost:
- sum active numeric parameters with semanticKey = "cost";
- require consistent units;
- sample uses EUR.

Process cost:
- for each active process, convert authoritative duration to hours;
- find active process —requiresResource→ resource relationships;
- for each assignment use resource.metadata.hourlyRate;
- use relationship.requiredQuantity;
- default missing quantity to 1 with warning;
- process resource cost = durationHours × hourlyRate × requiredQuantity;
- sum all active assignments.

Estimated total cost:
- direct element cost + process cost.

Total power:
- sum active numeric parameters with semanticKey = "power";
- sample uses kW.

Manufacturing lead time:
- use active process elements and active dependsOn relationships;
- detect cycles first;
- process without predecessors starts at 0;
- earliestStart = maximum earliestFinish of predecessors;
- earliestFinish = earliestStart + durationHours;
- lead time = maximum earliestFinish;
- show the critical predecessor chain;
- missing or non-positive duration is blocking.

Resource demand:
- for each active resource, sum durationHours × requiredQuantity across active process assignments;
- display resource-hours;
- do not claim capacity feasibility without capacity and availability.

Basic utilization:
- availableHours = capacityHours × availabilityPercent / 100;
- utilizationPercent = demandHours / availableHours × 100;
- missing capacity or availability = Not available;
- zero or negative available hours = error;
- above 100% = warning.

Throughput Proxy:
- 1 / manufacturingLeadTimeHours;
- unit 1/h;
- maximize;
- explicitly describe as a simplified comparative proxy, not actual production throughput.
