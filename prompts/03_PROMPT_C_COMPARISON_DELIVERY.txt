- The Trade Study Solution Space sequence is exactly: Build the 150% architecture; Define feature model and constraints; Map variability to architecture; Create valid configurations; Derive 100% architectures; Simulate architectures; Compare and decide.
- Problem Space Step 3 is one guided setup. It creates or activates a Trade Study, records the direct decision question, selects existing needs/objectives/active use cases, shows automatically derived requirements, links the single project-wide Root Feature, selects reusable variability axes and creates or edits only the needed canonical KPIs.
- Store variability axes in one reusable project catalogue. Each axis owns exactly one synchronized major FeatureGroup under the shared Root Feature. Rename both together; block deletion while the group contains features or nested groups.
- Persist one active Trade Study per project and use it for Dashboard Step 3 and Step 7 status. Show the synchronized selector in Dashboard details and the guided setup.
- Alternative selection belongs only to Solution Space Step 7, after current derivation and simulation evidence exists.
- Feature-model constraints are optional when selectable features exist and no feature-model or constraint errors remain.
- Alternatives must be valid configurations with current saved 100% derivations and current complete simulations tied to those exact derivations. At least two are required.
- Feasibility comes only from linked requirement formulas. Do not create Trade Study thresholds or KPI direction/weight overrides.
- KPI formula or algorithm, output unit, direction, weight and objective links are canonical and editable in the guided setup. Missing or stale evidence blocks comparison.
- Keep requirement-failing alternatives visible with diagnostic scores, but never prefer or approve them.
- Every selected KPI must be numeric and current for every alternative. Normalize each KPI using feasible alternatives only, then apply that same scale to infeasible diagnostic values.
- A sole feasible alternative may be selected with an explicit “no competitive feasible ranking” limitation.
- Manager and Expert views use identical evidence and calculations; Expert exposes more lineage and detail.
- Approval requires explicit feasible selection, rationale and baseline confirmation, and captures automatic evidence links.
- Use “simulate architecture(s)” in user-facing workflow language. Do not use “generate simulation evidence”.

Schema-8 projects migrate non-destructively to schema 9. Preserve existing studies and groups, select the first existing study as active, link a sole existing Root Feature, and offer existing FeatureGroups for explicit axis adoption without guessing. GLOBAL PRODUCT RULES

The product is a single-user, browser-based MBSE/MBPLE programme-preparation workbench. It demonstrates simplified digital-thread traceability, product/process/resource modeling, feature-based variability, deterministic 150%-to-100% derivation, preliminary KPI and pre-sizing calculations, architecture/configuration comparison, decisions, snapshots, and selective export.

The product may support small, bounded early-phase engineering studies. It is not:
- a certified engineering-analysis tool;
- a professional SysML, PLM, manufacturing-planning, configuration-management, or simulation platform;
- a regulatory-compliance system;
- a replacement for detailed physical simulation or verified design substantiation.

Every decision-relevant calculated or simulated result must display:

“Preliminary engineering estimate — not a verified detailed-design result.”

STUDY-SPECIFIC KPI SETTINGS

```ts
  maximum?: number;
  mode: "warning" | "hard";
}

  weight: number;
  optimizationDirection: "minimize" | "maximize";
  threshold?: ComparisonThreshold;
}
```

Rules:

- minimum must not exceed maximum;

NORMALIZATION

For each KPI, use only finite available values among selected alternatives.

For maximize:

normalized = 100 × (value - minimum) / (maximum - minimum)

For minimize:

normalized = 100 × (maximum - value) / (maximum - minimum)

Rules:
- clamp rounding artifacts to 0–100;
- if maximum equals minimum, assign 100 to every alternative with a value;
- explain that the KPI does not differentiate alternatives;
- missing values remain Missing, never zero;
- do not invent values.

WEIGHTED SCORING AND DATA COVERAGE

For each alternative:
- use only selected KPIs with available normalized values;
- renormalize applicable weights;
- weightedScore = sum(score × applicableWeight) / sum(applicableWeight);
- if no valid values remain, weighted score = Not available.

Calculate:

dataCoveragePercent =
available selected raw weight / total selected raw weight × 100

Show weighted score together with data coverage.

When alternatives use different KPI subsets:
- generate PMC-104;
- show which KPIs are missing;
- do not present scores as equally complete;
- do not declare an unqualified leader when a leading score has lower data coverage than another alternative.

Required label:

“Highest calculated score under the selected KPI weights, available data, documented assumptions, and shown data coverage.”

Never label an alternative universally optimal.
