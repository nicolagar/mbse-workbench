# Prompt A — Modeling Foundation

## MBSE/MBPLE Web Application — Stage A of A → B → C

ROLE

Act as a senior full-stack software architect, UX designer, systems engineer, and test engineer with expertise in MBSE, MBPLE, SysML-inspired modeling, product/process/resource modeling, feature-based configuration, early-phase pre-sizing, architecture trade studies, browser application architecture, safe expression parsing, data migration, and engineering UX.

GLOBAL PRODUCT RULES

The product is a single-user, browser-based MBSE/MBPLE programme-preparation workbench. It demonstrates simplified digital-thread traceability, product/process/resource modeling, feature-based variability, deterministic 150%-to-100% derivation, preliminary KPI and pre-sizing calculations, architecture/configuration comparison, decisions, snapshots, and selective export.

The product may support small, bounded early-phase engineering studies. It is not:
- a certified engineering-analysis tool;
- a professional SysML, PLM, manufacturing-planning, configuration-management, or simulation platform;
- a regulatory-compliance system;
- a replacement for detailed physical simulation or verified design substantiation.

Every decision-relevant calculated or simulated result must display:

“Preliminary engineering estimate — not a verified detailed-design result.”

Use:
- React;
- TypeScript with strict mode;
- Vite;
- Tailwind CSS;
- React Flow;
- Recharts where charts are required;
- Zustand;
- localStorage;
- Lucide React;
- Vitest for domain-engine and migration tests;
- React Testing Library where focused component tests provide value;
- a custom safe tokenizer/parser/evaluator for feature and KPI expressions;
- SheetJS only in Stage C for XLSX export;
- jsPDF only in Stage C for PDF export.

The application must:
- run entirely in the browser;
- require no backend, authentication, cloud service, or external API;
- make no runtime network calls;
- use no CDN-hosted assets, fonts, libraries, or icons;
- remain usable without internet access when run locally after dependencies are installed;
- preserve one canonical project model and one canonical Zustand store;
- persist edits in versioned localStorage;
- restore the active project after browser refresh;
- validate imported and persisted data defensively;
- never execute arbitrary user-entered code;

- provide honest empty states, validation messages, warnings, and limitations;
- contain no non-working mandatory controls;
- contain no TODO, FIXME, placeholder, mock-only, or “not implemented” behavior for mandatory requirements.

Prioritize, in order:
1. data integrity and safety;
2. correct deterministic engineering logic;
3. backward compatibility;
4. functional completeness;
5. transparent validation;
6. usability and accessibility;
7. visual polish.

ARCHITECTURE APPLICABILITY

Rules:
- architectureScope = "common" means architectureId must be undefined;
- architectureScope = "specific" means architectureId must reference an existing architecture;
- common elements are applicable to every architecture;
- specific elements are applicable only to their referenced architecture;
- every ElementType may be common or specific;
- architecture filtering always preserves common elements;
- a relationship with architectureId undefined is common;
- a relationship with architectureId set is applicable only to that architecture;
- relationship endpoints must be compatible with the relationship architecture context.

BASELINE AND ACTIVE ARCHITECTURE INVARIANTS

- At most one architecture may have status "baseline".
- When an architecture becomes baseline:
  - Project.baselineArchitectureId is set to that ID;
  - any previous baseline architecture becomes "candidate".
- Clearing the baseline removes baselineArchitectureId and changes the previous baseline to "candidate".
- Project.activeArchitectureId is a user context selection only and does not change architecture status.
- Deleting the active or baseline architecture requires confirmation and a clear explanation of affected elements and relationships.

TRACEABILITY METRICS

Calculate and display:
- Need coverage = needs connected to at least one requirement / total needs × 100.
- Requirement-to-function coverage = requirements connected to at least one function / total requirements × 100.
- Function-to-architecture coverage = functions connected to at least one logical or technical element / total functions × 100.
- Architecture-to-process coverage = technical elements connected to at least one realization process / total technical elements × 100.
- Process-to-resource coverage = processes connected to at least one required resource / total processes × 100.
- End-to-end coverage = needs for which at least one path exists through Need → Requirement → Function → Logical or Technical Element → Process → Resource / total needs × 100.

Show numerator, denominator, formula, and path interpretation for each metric. If a denominator is zero, show “Not available” and explain that no applicable source elements exist.

MODEL COMPLETENESS AND MATURITY

Model completeness:

completed applicable required fields / all applicable required fields × 100

Required-field checks:
- every element: non-empty name, description, status;
- numeric parameter with a value: unit;
- process: positive duration and duration unit;
- resource referenced by requiresResource: finite non-negative hourlyRate;
- specific element: valid architectureId.

Approval maturity:

approved elements / total elements × 100

Overall model maturity:

40% model completeness
+ 40% end-to-end traceability coverage
+ 20% approval maturity

If a component denominator is zero:
- display that component as Not available;
- exclude it from the weighted average;
- renormalize the remaining component weights;
- display the full calculation.
